GitHub Actions jobs,
each in its own microVM

BurstGrid is an open-source self-hosted runner platform. A central TypeScript scheduler receives GitHub webhooks, dispatches jobs to a fleet of EC2 bare-metal hosts over SSE, and each job boots into a dedicated Firecracker VM in under 200 ms—then disappears.

How it works

From pull request to runner in four hops

What happens from the moment a developer opens a PR to the moment a self-hosted runner picks up the job.

1
GitHub queues the workflow job and fires a webhook
When the PR is opened, GitHub evaluates .github/workflows/ci.yml. Any job with runs-on: [self-hosted, ...] is set to queued and GitHub immediately POSTs a workflow_job event to the webhook URL configured in the BurstGrid GitHub App.
POST /v1/webhook  —  X-GitHub-Event: workflow_job
{ "action": "queued", "workflow_job": { "id": 32145678, "run_id": 9821034, "labels": ["self-hosted", "linux", "burstgrid:size=large"], "status": "queued" }, "repository": { "full_name": "acme/monorepo" } }
2
Scheduler verifies the payload, mints a runner token, enqueues the job
BurstGrid verifies the X-Hub-Signature-256 header using the webhook secret from the GitHub App. It then authenticates as the App installation and calls the GitHub Runners API to generate a one-time runner registration token for the target repo. The job and token go into a priority queue partitioned by tier. If the queue exceeds maxQueueDepth, the scheduler returns 503—GitHub retries for up to 72 hours.
POST /repos/acme/monorepo/actions/runners/registration-token
// one-time token injected into the VM via kernel boot args { "token": "AABCDEFGHIJKLMNOPQ", "expires_at": "2026-08-25T11:30:00Z" }
3
Scheduler dispatches the assignment to a worker over SSE
The router checks each connected worker's free vCPU and RAM against the job's size label (burstgrid:size=large → 4 vCPU / 4 GiB). The first worker with matching capabilities and enough headroom receives the job as a JSON event on its persistent GET /v1/workers/:id/stream SSE connection. No polling, no database.
SSE → worker-i-0a3f2b  (persistent connection)
data: { "jobId": "3d9f...", "runnerToken": "AABCDEFGHIJKLMNOPQ", "labels": ["self-hosted", "linux", "burstgrid:size=large"], "vcpus": 4, "memoryMiB": 4096 }
4
Worker boots a Firecracker microVM, runner self-registers, job runs
The agent calls the Firecracker Unix socket API to boot a microVM with the requested resources. The runner token and labels are passed as kernel boot arguments—the Actions runner inside the VM reads /proc/cmdline, registers with GitHub, and picks up the queued job. On completion the VM is terminated, the slot freed, and the worker sends a heartbeat back with updated resource counts. The rootfs is never reused.
Firecracker API → PUT /boot-source
{ "kernel_image_path": "/opt/burstgrid/vmlinux", "boot_args": "console=ttyS0 reboot=k panic=1 RUNNER_TOKEN=AABCDEFGHIJKLMNOPQ RUNNER_LABELS=self-hosted,linux,burstgrid:size=large" }
Get started

From zero to running jobs

Five steps to deploy BurstGrid against your own GitHub organization. Steps 1–2 run in minutes; steps 3–4 take longer the first time you build a rootfs.

1
Create a GitHub App
Go to Settings → Developer Settings → GitHub Apps → New GitHub App. Set the webhook URL to https://your-scheduler/webhook/github and generate a secret. Grant Administration: read & write and Actions: read, then subscribe to workflow_job events. Download the private key PEM and install the App on your org.
Scheduler environment variables
GITHUB_APP_ID=123456 GITHUB_PRIVATE_KEY_PATH=/run/secrets/burstgrid.pem BURSTGRID_WEBHOOK_SECRET=your-webhook-secret
2
Deploy the scheduler
The scheduler is a Node.js process. Run it on any standard EC2 instance (t3.small is enough). It needs outbound HTTPS to api.github.com and inbound access on port 8080 from GitHub’s webhook IPs.
Docker
# Build from source docker build --target scheduler -t burstgrid-scheduler . docker run -p 8080:8080 \ -e GITHUB_APP_ID=123456 \ -e GITHUB_PRIVATE_KEY_PATH=/run/secrets/key.pem \ -e BURSTGRID_WEBHOOK_SECRET=secret \ -v /path/to/key.pem:/run/secrets/key.pem:ro \ burstgrid-scheduler
3
Build your rootfs image
Each Firecracker VM boots from a read-only ext4 rootfs containing the GitHub Actions runner binary. Your init script reads RUNNER_TOKEN and RUNNER_LABELS from /proc/cmdline, calls ./config.sh to register, then ./run.sh to execute the job. Optionally read REGISTRY_MIRROR to configure Docker’s pull-through cache.
/etc/init.d/burstgrid-runner (rootfs init script)
#!/bin/bash # Parse kernel cmdline args written by the scheduler TOKEN=$(grep -oP 'RUNNER_TOKEN=\K\S+' /proc/cmdline) LABELS=$(grep -oP 'RUNNER_LABELS=\K\S+' /proc/cmdline) MIRROR=$(grep -oP 'REGISTRY_MIRROR=\K\S+' /proc/cmdline || true) # Configure Docker pull-through cache if mirror is set [ -n "$MIRROR" ] && echo "{\"registry-mirrors\":[\"$MIRROR\"]}" > /etc/docker/daemon.json service docker start # Register and run the GitHub Actions runner (ephemeral) cd /opt/actions-runner ./config.sh --url "$REPO_URL" --token "$TOKEN" --labels "$LABELS" --ephemeral --unattended ./run.sh
4
Deploy worker agents on bare-metal EC2
Workers must run on bare-metal instances (e.g. m7i.metal-24xl, m6g.metal) because Firecracker requires KVM. Standard virtualized instances can’t run nested VMs. Copy the rootfs image and kernel to each host, then run the worker agent.
Worker agent environment
BURSTGRID_SCHEDULER_URL=http://10.0.1.50:8080 BURSTGRID_WORKER_ID=$(curl -s http://169.254.169.254/latest/meta-data/instance-id) BURSTGRID_VM_IMAGE=/var/lib/burstgrid/runner.img BURSTGRID_KERNEL=/var/lib/burstgrid/vmlinux BURSTGRID_SLOTS=8 # concurrent VMs per host BURSTGRID_VCPUS=48 # match your instance type BURSTGRID_MEMORY_MIB=98304 # 96 GiB BURSTGRID_CAPABILITIES=linux,x86_64,docker BURSTGRID_REGISTRY_MIRROR=http://10.0.1.50:5000 # optional
5
Point your workflows at BurstGrid
Add self-hosted plus a burstgrid:size= label to any job’s runs-on. No other workflow changes needed. GPU jobs add a gpu label and are routed to workers that advertise the gpu capability.
.github/workflows/ci.yml
jobs: test: runs-on: [self-hosted, linux, burstgrid:size=large] steps: - uses: actions/checkout@v4 - run: pnpm test train: runs-on: [self-hosted, linux, gpu, burstgrid:size=4xlarge] steps: - run: python train.py
What's inside

Built for teams who've hit the ceiling

GitHub-hosted runners top out at 4 vCPU / 16 GiB. BurstGrid hands you the metal.

Firecracker isolation

Every job gets its own kernel. No shared namespaces, no container breakout surface. The rootfs is discarded when the runner exits.

SSE dispatch

Workers hold a persistent Server-Sent Events connection. Jobs arrive the instant they’re queued—no polling, no long-poll timeouts, no extra infra.

Resource-aware routing

Sizes from small (1 vCPU / 1 GiB) to 8xlarge (64 vCPU / 128 GiB). Jobs only dispatch to workers with enough free headroom. No overcommit.

GPU & bare-metal routing

Label jobs with gpu and register GPU hosts in process mode. The scheduler routes exclusively to workers advertising that capability—no Firecracker needed on GPU hosts.

Registry pull-through cache

Point workers at a local Docker registry mirror. Pulled layers cache on the host and are reused across all VMs. First pull hits Docker Hub; every job after that is served at LAN speed.

Per-tier autoscaling

Define separate EC2 launch templates per fleet. Each scales independently against its own queue threshold. Workers drain naturally—no forced termination.

Circuit breaker

GitHub API calls trip after 5 consecutive failures, open for 30 s. Returns 503 so GitHub keeps retrying for up to 72 hours—no events lost.

Optional backends

Attach Redis for queue durability and worker persistence, SQS as an additional job source, and DynamoDB for an append-only job history log. All optional, all env-var configured.

OpenTelemetry metrics

Queue depth, dispatch latency, VM boot time, job duration—all OTLP. Drop the included OTel Collector config on each host and ship to Grafana or Datadog.
