Self-hosted GitHub Actions
on Firecracker microVMs

BurstGrid is an open-source CI runner platform. Each job runs in an isolated Firecracker microVM, dispatched by a central TypeScript scheduler over SSE, with per-tier EC2 autoscaling.

View on GitHub See how it works

⚠ Current Status

BurstGrid is in early development. The architecture, scheduler, autoscaler, and telemetry pipeline are designed and coded, but none of this has been run end-to-end in a real AWS environment. There are no Firecracker boot tests, no live webhook tests, and no production traffic validation yet.

We're open-sourcing the design early so teams building similar infrastructure can follow along and contribute. Expect breaking changes. The API surface, config schema, and deployment model are all subject to change before a stable release.

Why BurstGrid

Built for teams who've outgrown hosted runners

GitHub-hosted runners cap out at 4 vCPU / 16 GB RAM. BurstGrid puts you in control of the metal.

🔥

Firecracker microVMs

Every job boots into a fresh Firecracker VM in <200ms. Full kernel isolation, no container breakout risk, rootfs discarded on completion.

📡

SSE dispatch

Workers hold a persistent Server-Sent Events connection to the scheduler. No polling, no long-poll timeouts — jobs arrive over the wire the moment they're queued.

⚖️

Resource-aware scheduling

Label jobs with burstgrid:size=large to request specific vCPU + RAM. The scheduler only assigns jobs to workers with enough free resources.

📈

Per-tier autoscaling

Define separate EC2 launch templates for standard, large, and xlarge job tiers. Each fleet scales independently based on queue depth.

🛡️

Circuit breaker + retry

GitHub API calls are wrapped in a circuit breaker (5-failure threshold, 30s cooldown) with exponential backoff. The scheduler returns 503 so GitHub retries for up to 72 hours.

📊

OpenTelemetry metrics

Queue depth, dispatch latency, VM boot time, and job duration are all emitted as OTLP metrics. Drop the included OTel Collector config on each host and point it at Grafana, Datadog, or Prometheus.

Architecture

How it works

A lightweight TypeScript scheduler sits in front of a fleet of metal EC2 workers, each running multiple isolated microVMs.

Job Sizing

Pick the right VM for the job

Add a label to your workflow to route a job to the right fleet.

.github/workflows/ci.yml 
runs-on: [self-hosted, linux, burstgrid:size=large]

# or for a monorepo lint job that needs the full machine:
runs-on: [self-hosted, linux, burstgrid:size=xlarge]
Size label vCPU RAM Typical EC2 host Slots/host
small 1 1 GiB m6i.metal (8+ slots) 8–32
medium 2 2 GiB m6i.metal 8–16

Configuration

One YAML file to rule them all

Drop burstgrid.config.yaml at the project root. Every field is optional — env vars take precedence.

burstgrid.config.yaml 
scheduler:
  maxQueueDepth: 500      # 503 above this; GitHub retries for 72 h

autoscaler:
  enabled: true
  evaluationIntervalSec: 30
  fleets:
    - name: standard
      launchTemplateId: lt-xxxxxxxxxxxxxxxxx
      maxWorkers: 50
      slotsPerWorker: 8
      scaleUpThreshold: 4
    - name: xlarge
      sizeTag: burstgrid:size=xlarge
      launchTemplateId: lt-yyyyyyyyyyyyyyyyy
      maxWorkers: 5
      slotsPerWorker: 1
      scaleUpThreshold: 1
