One job.
One microVM.
Nothing shared.

BurstGrid dispatches every GitHub Actions job to a fresh Firecracker microVM on your own EC2 bare-metal fleet. Separate kernel, separate Docker daemon, separate everything. Gone the moment the job completes. No shared state. No secret bleed. No per-minute GitHub pricing.

Fit

Is BurstGrid right for you?

BurstGrid is not the right tool for everyone. Here is when it makes sense and when it does not.

Good fit
  • High concurrency
    Running 20+ jobs simultaneously most of the day. Density on bare-metal beats per-instance EC2 pricing above roughly 15 concurrent jobs.
  • Strict isolation requirements
    SOC 2, HIPAA, or FedRAMP workloads where kernel-level isolation per job is required. Containers share a kernel; microVMs do not.
  • Reproducible build environments
    You own the rootfs image. Bake your exact toolchain once, version it in git, and every job boots from an identical filesystem. No runtime package downloads, no AMI drift.
  • Mixed CPU + GPU CI pipelines
    One scheduler routes both standard jobs to Firecracker microVMs and GPU/ML jobs to dedicated GPU EC2 hosts. No separate runner groups to manage.
  • Fast feedback loops matter
    150ms VM boot vs 90s EC2 cold start. For short jobs on commit-heavy repos, that gap is most of the total CI wait time.
Not a good fit
  • Low volume
    Under ~50 jobs per day, a per-job EC2 runner or GitHub-hosted runners are simpler and cheaper. Bare-metal has a floor cost even at zero jobs.
  • Already on Kubernetes
    ARC (Actions Runner Controller) integrates directly with your existing cluster. If you are already on EKS or GKE the operational overlap is zero and ARC is the right choice.
  • Windows runners
    Firecracker is Linux-only. Windows jobs are not supported.
  • Highly variable load
    Warm bare-metal hosts are required for fast dispatch. Scaling to zero kills the DX. If your CI load is unpredictable and spiky, per-job EC2 runners are a better match.
The flow

Webhook to running job in four hops

No polling. No message broker. No Kubernetes. Just a webhook, a queue, a persistent SSE connection, and a VM that exists for exactly as long as the job does.

1
GitHub fires a workflow_job webhook
The moment a workflow job is queued, GitHub POSTs a signed workflow_job event to your scheduler. BurstGrid verifies the X-Hub-Signature-256 HMAC before doing anything else. If the signature doesn’t match, the request is dropped. If the queue is full, it returns 503; GitHub will retry the delivery for up to 72 hours, so nothing is lost.
POST /v1/webhook  —  X-GitHub-Event: workflow_job
{ "action": "queued", "workflow_job": { "id": 32145678, "run_id": 9821034, "labels": ["self-hosted", "linux", "burstgrid:size=large"], "status": "queued" }, "repository": { "full_name": "acme/monorepo" } }
2
Scheduler mints a runner token and enqueues the job
BurstGrid authenticates as your GitHub App installation and calls the Runners API to generate a one-time registration token for the target repo. The token and job metadata go into a priority queue partitioned by tier. critical jobs always jump ahead of standard ones. Token generation is protected by a circuit breaker: after 5 consecutive GitHub API failures, the scheduler opens the circuit and returns 503 until the API recovers.
POST /repos/acme/monorepo/actions/runners/registration-token
// one-time token injected into the VM via kernel boot args { "token": "AABCDEFGHIJKLMNOPQ", "expires_at": "2026-08-25T11:30:00Z" }
3
Router matches the job to a worker and pushes over SSE
The router checks the job’s size label (burstgrid:size=large → 4 vCPU / 4 GiB) against every connected worker’s free resources and capability labels. The first worker that fits gets the assignment pushed as a JSON event over its persistent SSE connection, the same open HTTP response it’s been holding since it registered. No database read. No poll. Dispatch latency is typically under 5 ms.
SSE → worker-i-0a3f2b  (persistent connection)
data: { "jobId": "3d9f...", "runnerToken": "AABCDEFGHIJKLMNOPQ", "labels": ["self-hosted", "linux", "burstgrid:size=large"], "vcpus": 4, "memoryMiB": 4096 }
4
Worker boots a Firecracker VM; runner picks up the job
The worker agent calls the Firecracker Unix socket API to boot a microVM with exactly the requested vCPU and RAM. The runner token and size labels are injected as kernel boot args; the init script inside the VM reads /proc/cmdline, calls ./config.sh --ephemeral to register with GitHub, then ./run.sh to execute the job. When it exits, the VM is killed, the disk is discarded, and the slot is freed. The rootfs is never reused.
Firecracker API → PUT /boot-source
{ "kernel_image_path": "/opt/burstgrid/vmlinux", "boot_args": "console=ttyS0 reboot=k panic=1 RUNNER_TOKEN=AABCDEFGHIJKLMNOPQ RUNNER_LABELS=self-hosted,linux,burstgrid:size=large" }
Get started

From zero to running jobs

Five steps to deploy BurstGrid against your own GitHub organization. Steps 1–2 run in minutes; steps 3–4 take longer the first time you build a rootfs.

1
Create a GitHub App
Go to Settings → Developer Settings → GitHub Apps → New GitHub App. Set the webhook URL to https://your-scheduler/webhook/github and generate a secret. Grant Administration: read & write and Actions: read, then subscribe to workflow_job events. Download the private key PEM and install the App on your org.
Scheduler environment variables
GITHUB_APP_ID=123456 GITHUB_PRIVATE_KEY_PATH=/run/secrets/burstgrid.pem BURSTGRID_WEBHOOK_SECRET=your-webhook-secret
2
Deploy the scheduler
A single Node.js process. Runs on any standard EC2 instance; t3.small handles thousands of webhooks per minute. It needs outbound HTTPS to api.github.com and inbound port 8080 from GitHub’s webhook IP ranges. No database required to start; add Redis later if you need queue durability across restarts.
Docker
# Build from source docker build --target scheduler -t burstgrid-scheduler . docker run -p 8080:8080 \ -e GITHUB_APP_ID=123456 \ -e GITHUB_PRIVATE_KEY_PATH=/run/secrets/key.pem \ -e BURSTGRID_WEBHOOK_SECRET=secret \ -v /path/to/key.pem:/run/secrets/key.pem:ro \ burstgrid-scheduler
3
Build your rootfs image
Each Firecracker VM boots from a small ext4 image you build once and store on each host. Copy rootfs/template/Dockerfile into a new folder named after your image, customise it for your toolchain, then run the build script. Every image is just a folder with a single Dockerfile that fully declares what is in it. The BurstGrid init script (scripts/vm-init.sh) is injected automatically. It reads RUNNER_TOKEN and RUNNER_LABELS from /proc/cmdline and starts the runner as an ephemeral instance.
rootfs/ layout
rootfs/ template/ Dockerfile # base template, copy this ubuntu-docker/ Dockerfile # Ubuntu 22.04 + Docker 24 node20/ Dockerfile # Ubuntu 22.04 + Node 20 my-custom-image/ Dockerfile # your image
Build and register an image
# 1. scaffold a new image from the template cp -r rootfs/template rootfs/my-image # 2. edit rootfs/my-image/Dockerfile # 3. build the .img (requires docker + e2fsprogs) ./scripts/build-rootfs.sh rootfs/my-image/Dockerfile /opt/images/my-image.img 4G
4
Deploy worker agents on bare-metal EC2
Firecracker requires KVM, so workers must run on bare-metal instances. m7i.metal-24xl, m6g.metal, and similar are supported. Standard virtualized instances cannot run nested VMs. Copy the rootfs image and kernel to each host, set the environment variables below, and start the agent. The agent registers itself with the scheduler, opens an SSE stream, and starts accepting jobs immediately.
Worker agent environment
BURSTGRID_SCHEDULER_URL=http://10.0.1.50:8080 BURSTGRID_WORKER_ID=$(curl -s http://169.254.169.254/latest/meta-data/instance-id) BURSTGRID_VM_IMAGE=/var/lib/burstgrid/runner.img BURSTGRID_KERNEL=/var/lib/burstgrid/vmlinux BURSTGRID_SLOTS=8 # concurrent VMs per host BURSTGRID_VCPUS=48 # match your instance type BURSTGRID_MEMORY_MIB=98304 # 96 GiB BURSTGRID_CAPABILITIES=linux,x86_64,docker BURSTGRID_REGISTRY_MIRROR=http://10.0.1.50:5000 # optional
5
Point your workflows at BurstGrid
Add self-hosted plus a burstgrid:size= label to any job’s runs-on. That’s the only workflow change required. The scheduler reads the labels, picks the right worker, and boots a VM sized to match. GPU jobs add a gpu label and land exclusively on workers that advertise that capability. No routing config needed on your end.
.github/workflows/ci.yml
jobs: test: runs-on: [self-hosted, linux, burstgrid:size=large] steps: - uses: actions/checkout@v4 - run: pnpm test train: runs-on: [self-hosted, linux, gpu, burstgrid:size=4xlarge] steps: - run: python train.py
Custom images

Your Dockerfile is your image spec

Every rootfs is built from a Dockerfile you own. Copy the template, add your tools, build once, reference by name. The image catalog in config maps label names to paths with no hardcoded conventions.

1
Start from the template
rootfs/template/Dockerfile is a commented starting point. Every section (base OS, system packages, Docker daemon, language runtimes, pre-warmed caches, runner binary) is labelled and optional. Copy it and delete what you don’t need.
rootfs/my-image/Dockerfile (after copying template)
FROM ubuntu:22.04 RUN apt-get update && apt-get install -y \ ca-certificates curl git libicu70 libssl3 \ python3 python3-pip build-essential # your additions # pre-warm pip cache so jobs don’t wait for installs RUN pip install pytest boto3 requests # runner binary (required) ARG RUNNER_VERSION=2.317.0 RUN mkdir -p /opt/actions-runner && cd /opt/actions-runner \ && curl -fsSL "https://github.com/actions/runner/releases/download/v${RUNNER_VERSION}/actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz" \ | tar -xz && ./bin/installdependencies.sh
2
Build the .img
scripts/build-rootfs.sh uses docker export + mkfs.ext4 to turn any Dockerfile into a bootable ext4 image. It also injects scripts/vm-init.sh as /sbin/burstgrid-init, the PID 1 script that reads /proc/cmdline, starts Docker if present, and runs the Actions runner as ephemeral before halting the VM.
Build (run on the build host, not the worker)
./scripts/build-rootfs.sh \ rootfs/my-image/Dockerfile \ /opt/images/my-image.img \ 4G # image size — set generously, sparse file # copy to workers via S3 or scp: aws s3 cp /opt/images/my-image.img s3://your-bucket/rootfs/my-image.img ssh worker-01 "aws s3 cp s3://your-bucket/rootfs/my-image.img /opt/images/"
3
Register and use
Add the image to the worker.images catalog in burstgrid.config.yaml. The name field is what jobs put in their runs-on label. All other fields are metadata; they document what’s in the image so your team doesn’t have to guess.
burstgrid.config.yaml
worker: images: - name: my-image # used in runs-on path: /opt/images/my-image.img description: "Ubuntu 22.04 + Python 3 + pytest" os: ubuntu-22.04 tools: [python3, pip, git, curl]
.github/workflows/ci.yml
jobs: test: runs-on: [self-hosted, burstgrid:image=my-image]
GPU / AI

GPU jobs run directly on the host

Firecracker has no GPU passthrough. GPU and ML jobs are routed to dedicated EC2 GPU instances that run the Actions runner natively, with no microVM in the path. The host AMI is pre-baked with CUDA, ML frameworks, and optionally Docker + NVIDIA Container Toolkit.

1
Define a GPU AMI profile
Build an EC2 AMI with your GPU stack pre-installed (CUDA drivers, PyTorch, model weights, etc.). Register it in burstgrid.config.yaml under gpu_amis. Docker and the NVIDIA Container Toolkit can be included. docker run --gpus all works natively on the host.
burstgrid.config.yaml
gpu_amis: - id: ami-0abc1234 name: cuda12-pytorch2 cuda_version: "12.4" instance_families: [g4dn, g5, p3] docker_enabled: true cached_packages: [torch==2.3.0, transformers==4.40.0] cached_models: [meta-llama/Llama-3-8B-Instruct] pre_pulled_images: [pytorch/pytorch:2.3.0-cuda12.1-runtime] env: TORCH_HOME: /opt/model-cache
2
Configure the GPU autoscaler fleet
Add a fleet entry with gpu_ami_id and instance_type. The autoscaler passes these as overrides to RunInstances on top of your base Launch Template. Workers on these instances should register with gpu and cuda in their capabilities; only GPU-labelled jobs will land on them.
autoscaler fleet + workflow label
# burstgrid.config.yaml autoscaler: fleets: - name: gpu-ai size_tag: burstgrid:gpu launch_template_id: lt-gpu-base gpu_ami_id: ami-0abc1234 instance_type: g4dn.xlarge max_workers: 5 slots_per_worker: 1 # 1 job at a time on each GPU host scale_up_threshold: 0 subnet_ids: [subnet-gpu-az1] # workflow runs-on: [self-hosted, burstgrid:gpu] # routes to gpu-ai tier runs-on: [self-hosted, burstgrid:gpu-ai] # equivalent alias
Why BurstGrid

Container isolation isn't enough

When jobs handle secrets, run privileged operations, or modify the Docker daemon, sharing a kernel is a liability. VM-per-job removes the class of problem entirely.

Separate kernel per job

Not a container. Not a namespace. A real Firecracker microVM with its own kernel, booted in under 200 ms and destroyed on exit. The disk never touches the next job.

Sub-5 ms dispatch

One persistent SSE connection per worker. The scheduler pushes job assignments the instant they’re dequeued, with no polling, no broker, no cold-start reconnect per job.

Right-sized, not over-provisioned

Seven sizes from small (1 vCPU) to 8xlarge (64 vCPU / 128 GiB). Jobs only dispatch to workers with the headroom to match. No overcommit, ever.

GPU jobs go straight to metal

Register GPU hosts in process mode with a gpu capability label. Jobs that need GPU land exclusively on those hosts. Firecracker isn’t in the critical path.

Docker pulls that don’t start from zero

Point workers at a local registry mirror. The first VM pulls from Docker Hub and caches on the host. Every VM after that is served at LAN speed. ECR pull-through cache works too.

Scale the right fleet, not all of them

Separate EC2 launch templates per size tier. Each one scales independently against its own queue depth. Workers drain naturally, with no forced termination mid-job.

GitHub goes down. Your queue doesn’t.

The circuit breaker trips after 5 consecutive API failures and returns 503. GitHub retries webhook deliveries for up to 72 hours. No events are dropped.

Durable when you need it

Attach Redis for queue persistence and worker state, SQS as a webhook alternative, or DynamoDB for an append-only job history log. All opt-in, all env-var configured.

Metrics from day one

Queue depth, dispatch latency, VM boot time, job duration, all emitted as OTLP. Drop the included OTel Collector config on each host and ship to Grafana or Datadog.
